## これは何？
サイトのBF記事とトップの「期間限定」欄は、時刻で自動的に
「開催前 → 開催中 → 終了」に変わります。
ただし **サイトを作り直して（ビルド）公開し直さないと、公開ページは変わりません**。
そこで、GitHub（サイトの置き場所）に「決まった時刻に自動で作り直す」設定を足しました。
（ファイル：`.github/workflows/scheduled-rebuild.yml`／GitHubの無料枠だけ使用）

## 自動で作り直す時刻（日本時間）
| いつ | 何が変わる |
|---|---|
| 11/19(木) 20:05 と 20:35 | 「開催前」→「開催中」 |
| 11/25(水) 02:05 と 02:35 | 「開催中」→「終了」 |

- GitHubの定時実行は混むと数分〜数十分遅れることがあります（だから30分後にもう1回）
- 中身が変わらないときは何もしません（来年の同じ日に動いても害なし）
- 作り直したら、Bingなどへの「更新しました」の通知（IndexNow）も、変わったページだけ送ります

## 手でやる場合（自動が動かなかったとき）
リポジトリのフォルダで（commit＝変更の記録、push＝GitHubに送って公開）：
```
git pull --rebase && python3 build.py && git add -A docs && git commit -m "BF表示の切替" && git push
```
（`git add -A docs` にしているのは、作業途中の別ファイルを一緒に公開しないため。変化がなければ commit で止まるが問題なし）
GitHubの画面からなら：Actions → 「Scheduled rebuild」→「Run workflow」ボタンでも同じことができます。

## うまくいかないときの切り分け（上から順に）
1. **自動の作り直しが動いたか**：GitHub → Actions →「Scheduled rebuild」に、その時刻の実行があるか。
   なければ遅れか未実行 →「Run workflow」で手動実行、または上の手順で手でやる。
   （定時実行は、リポジトリに60日間動きがないと止まる仕様。今は毎日更新しているので問題なし）
2. **実行が赤（失敗）か**：実行を開いて、どの段で止まったか見る。
   「ビルド」の段ならbuild.pyのエラー → 手元で `python3 build.py` を実行して同じエラーが出るか確認。
   「push」の段なら、同時に別の回がpushしていた可能性 → もう一度「Run workflow」。
3. **成功しているのにページが古い**：GitHub → Actions の「pages build and deployment」（公開の処理）が
   その後に動いて成功しているか。動いていなければ、手で何か1つpushすると公開し直されます。
   動いていれば、数分待って再読み込み（ブラウザの古い控えを見ている）。
